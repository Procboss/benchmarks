pboss vs pup — managing a Deno HTTP server

The same server.ts, the same Deno binary, the same machine, the same load — the only difference is which process manager supervises it. This measures the overhead of managing a Node server, not Node's raw HTTP performance. Both supervision models are covered: fork (one managed process) and cluster (2 workers) — and for Deno apps BOTH managers cluster natively (pboss: SO_REUSEPORT workers; pup: its built-in load balancer), so this is the apples-to-apples cluster comparison the bun edition of this repo cannot make (pm2 cannot cluster a Bun app).

Methodology

  • Every measured run starts from a verified-clean state: app deleted, daemon killed, port free, no orphaned processes — each run is a cold start of the whole manager stack (that cold-start time is itself measured).
  • A discarded warmup run precedes every measured run.
  • Manager order alternates between runs (load index + repeat parity) so time-of-run bias cannot favor one column.
  • CPU and memory cover the whole process tree (daemon + managed Node server), sampled from /proc every 0.5s during the measured run.
  • Crash-recovery and restart-storm runs are separate phases and never overlap the HTTP measurements.
  • Same-machine caveat: the load generator shares the CPUs with the servers; absolute numbers are specific to this box — compare the two columns, don't quote them as platform throughput.
  • Cluster mode runs the same matrix with N workers per manager — and for Deno apps BOTH managers cluster natively (pboss: SO_REUSEPORT workers; pup: its built-in load balancer), so the worker count and the sharing mechanism are identical on both sides: pboss's --instances N spawns a supervised wrapper primary that forks the workers; pm2's -i N makes the pm2 daemon itself the primary. The only variable stays the manager.

Winner names the column that scored better; the percentage beside it is the relative difference (pboss − pm2) / pm2 × 100 — positive means pboss scored the higher number. For throughput higher is better; for every other metric in these tables lower is better, and the Winner column already accounts for the direction. A row that is exactly level reads “tie”.

Cluster mode2 workers

The worker count and the sharing mechanism are identical; only the manager differs.

Reproduce

cd benchmarks/deno
npm install                     # pm2 + autocannon (local, pinned)
bash scripts/benchmark.sh       # default profile — BENCH_PROFILE=smoke first
BENCH_PROFILE=full bash scripts/benchmark.sh    # + the 1000-conn stress level
BENCH_INSTANCES=4 bash scripts/benchmark.sh      # cluster workers (default: cores)
# PBOSS_CMD="bun run /path/to/pboss/src/main.ts" bash scripts/benchmark.sh
Raw data: every number above traces to a file under results/raw/ — run.jsonl records, full autocannon JSON, /proc resource CSVs, recovery and storm event logs (fork and cluster each). results/summary.csv is the same data in one sheet. Don't read one run — the medians and the per-run notes show the repeats and the variability; a single run never decides a column.
