# pboss vs pup — managing a Deno HTTP server (fork + cluster modes)

A reproducible benchmark comparing **pboss** and **[pup](https://github.com/hexagon/pup)**
as process managers for the **same Deno HTTP server**, on one machine, under
identical load — in both supervision models: **fork** (one managed process)
and **cluster** (N workers behind one client-facing port).

For Deno apps, **both managers cluster natively — each with its own model**:

- **pboss** `--instances N` — its process-based cluster: N workers all
  binding the **same port** through `SO_REUSEPORT`, the kernel balancing
  connections across them.
- **pup** `cluster { instances, commonPort, startPort }` — its built-in
  **load balancer** on the common port, fronting N backend processes that
  each listen on their own private port (`startPort + i`, injected as
  `PUP_CLUSTER_PORT`).

The client-facing port and the worker count are identical on both sides;
only the manager (and its cluster model) differs.

What it measures is the **overhead of managing** a Deno server —
supervision, spawn route, daemon cost — not Deno's raw HTTP performance and
not application logic. The application is deliberately minimal
(`server.ts`): one fixed-body route and one `/health` route, no framework,
no database.

The full measured comparison lives in [`results/REPORT.md`](results/REPORT.md)
and as a self-contained page in [`results/REPORT.html`](results/REPORT.html)
(regenerated by `scripts/summarize.mjs` from the committed raw data). A
headline summary is reproduced below.

## Architecture

```
                    ┌──────────────────┐
                    │  autocannon      │  load generator (node)
                    │  c=10…1000       │  same machine, fixed payload
                    └────────┬─────────┘
                             │ HTTP
              ┌──────────────┴───────────────┐
              ▼                              ▼
     ┌────────────────┐             ┌────────────────┐
     │      pup       │             │     pboss      │
     │  (instance,   │             │    (daemon)    │
     │   deno)        │             │                │
     └───────┬────────┘             └───────┬────────┘
             │ spawns                       │ spawns
             ▼                              ▼
     ┌────────────────────────────────────────────┐
     │  deno server.ts  — THE SAME APPLICATION   │
     │  fork:    1 process                        │
     │  pboss cluster: N workers, one SO_REUSEPORT│
     │  pup cluster:    N backends behind pup's   │
     │                  load balancer             │
     └────────────────────────────────────────────┘
```

Both managers launch the exact same file with the exact same Deno binary
(pinned absolute `DENO_BIN`; pup's `cmd` spells it out, pboss's
`--interpreter` pins it), same port, same environment. The ONLY difference
between the two columns of every table is which process manager supervises
the server.

### Cluster mode, natively on both sides — with different models

There is no `node:cluster` for a Deno app, so each manager ships the
clustering it believes in, and this suite runs each one's native model at
the same worker count:

- **pboss** runs one process per worker, all binding the same port through
  `SO_REUSEPORT` — the kernel distributes connections. No proxy sits in
  the request path; a dead worker's connections are simply distributed to
  the survivors by the next connect.
- **pup** runs one backend process per worker on private ports and its own
  load balancer (inside the instance) on the common port — a userland
  round-robin proxy in the request path with backend health validation.

Both models answer the same benchmark URL; the throughput, latency and
CPU/memory tables therefore include each manager's honest cost of its own
clustering model. That is the comparison a Deno user actually chooses
between.

### The managers under test

| | pboss | pup |
| --- | --- | --- |
| Model | daemon (auto-spawned) | one `pup run` instance per config file |
| Registry | CLI flags → process dump in `PBOSS_HOME` | `pup.json` config file (the config IS the registry) |
| App start (warm) | `pboss start …` (daemon forks the process) | `pup start <id>` (IPC to the instance) |
| Restart | `pboss restart <name>` | `pup restart <id>` (IPC) |
| Crash policy (defaults) | healthy workers replaced immediately; boot-crash backoff 100 ms doubling to 2 s | `restart: "always"` with a 10 s restart delay (pup's default) |
| Cluster (Deno) | `--instances N` → SO_REUSEPORT workers | `cluster{instances, commonPort, startPort}` → load balancer + backends |
| Daemon cost | the pboss daemon under its runtime | the pup instance — a full Deno process |

Both managers are run with their **out-of-the-box** restart policies — the
comparison is "as installed", exactly like the node and bun suites. A pup
user can lower `restartDelayMs`; a pboss user can set `--restart-delay`.
Defaults are what most installs actually run.

## What is measured

- **Throughput / latency / errors** — autocannon from the same machine at
  c=10/100/500, 60 s per run, 5 repeats per manager, manager order
  alternating; a discarded warmup precedes every measured run.
- **CPU / memory** — the WHOLE process tree (daemon/instance + every
  worker/backend) sampled from `/proc` every 500 ms while load runs, plus a
  daemon-only idle measurement with no application.
- **Cold startup** — manager down → app serving `/health` (the daemon or
  instance boots too; that is the honest cost of a fresh install).
- **Warm startup** — daemon already up → app serving `/health`.
- **Crash recovery (fork)** — `SIGKILL` the server process, measure how
  long until `/health` answers again.
- **Worker respawn (cluster)** — `SIGKILL` ONE worker; measure how fast a
  replacement worker exists again and whether `/health` stayed up at all.
- **Restart storm** — manager-level restart N times in a row; failed
  starts, orphaned processes, per-restart wall time, and RSS before/after
  (leak check).

## Running it

```bash
# prerequisites: deno on PATH, pup installed (deno install -g jsr:@pup/pup),
# node (for autocannon + the /proc sampler), bun (for the tests)
npm install                     # autocannon (local, pinned)

bash scripts/benchmark.sh       # default profile — BENCH_PROFILE=smoke first
BENCH_PROFILE=smoke bash scripts/benchmark.sh   # ~5 min harness verification
BENCH_PROFILE=full bash scripts/benchmark.sh    # + the 1000-conn stress level
BENCH_INSTANCES=4 bash scripts/benchmark.sh     # cluster workers (default: cores)

# from a pboss repo checkout instead of an installed CLI:
PBOSS_CMD="bun run /path/to/pboss/src/main.ts" bash scripts/benchmark.sh

# crash recovery + restart storm alone (they are part of the full run):
bash scripts/crash-recovery.sh
BENCH_MODE=cluster bash scripts/crash-recovery.sh

node scripts/summarize.mjs      # regenerate REPORT.md / REPORT.html / summary.csv
```

The report and the README summary below are regenerated from whatever raw
data is on disk — the results committed here reproduce exactly.

### Isolation & safety

Each manager gets its own scratch home (a `mktemp -d` that is deleted on
exit): `PBOSS_HOME` for pboss, a per-run directory holding pup's config and
its `.pup/` runtime state (IPC port, secret, logs). Nothing touches a real
install; the only shared resources are the benchmark port (3000 by default,
`BENCH_PORT`) and the machine. Every measured run verifies a clean state
first: both managers down, port free, zero stray server processes — a run
that cannot reach that state is skipped, never measured dirty.

## Fairness rules

- Same `server.ts`, same pinned `DENO_BIN`, same port, same environment,
  same machine, same load — for BOTH managers, in BOTH modes.
- Manager order alternates (load index + repeat parity) so time-of-run bias
  cannot favor one column.
- Cluster mode runs the SAME matrix at the SAME worker count
  (`BENCH_INSTANCES`, default: one per core) on both managers — each with
  its own native clustering model (documented above).
- Every measured run starts from a verified-clean state; cold start is
  measured on every single run.
- A discarded warmup run precedes every measured run.
- Crash and storm tests run separately from throughput phases (a restart
  would contaminate the HTTP numbers).
- A cluster run must actually have N workers before anything is measured —
  one worker would be fork numbers wearing a cluster label; more than N
  would mean a respawn loop. Either way: skip, never measure a lie.

### Chunked execution (environments that cap process lifetime)

A full profile takes hours on a small box; the orchestrator supports
splitting it across sessions — every chunk ends with a summarize, so the
report and the README always reflect exactly the data accumulated so far:

```bash
# chunk 1 (fresh results): idle + startup phases
BENCH_PHASES=idle,warm-fork,warm-cluster bash scripts/benchmark.sh
# chunks 2..N (append): one (mode × load × repeat-window) at a time
BENCH_APPEND=1 BENCH_PHASES=matrix-fork  BENCH_START_REPEAT=1 BENCH_END_REPEAT=2 bash scripts/benchmark.sh
BENCH_APPEND=1 BENCH_PHASES=matrix-fork  BENCH_START_REPEAT=3 BENCH_END_REPEAT=5 bash scripts/benchmark.sh
BENCH_APPEND=1 BENCH_PHASES=matrix-cluster BENCH_START_REPEAT=1 BENCH_END_REPEAT=3 bash scripts/benchmark.sh
BENCH_APPEND=1 BENCH_PHASES=crash-fork,crash-cluster bash scripts/benchmark.sh
```
