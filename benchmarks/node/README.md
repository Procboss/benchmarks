# pboss vs pm2 — managing a Node HTTP server (fork + cluster modes)

A reproducible benchmark comparing **pboss** and **pm2** as process managers
for the **same Node HTTP server**, on one machine, under identical load — in
both supervision models: **fork** (one managed process) and **cluster**
(N workers sharing one port).

For Node apps, **both managers cluster natively through `node:cluster`** —
pm2's `-i N` is true cluster mode (the pm2 daemon becomes the cluster
primary), and pboss's `--instances N` spawns a supervised node:cluster
wrapper primary that forks the workers. This suite is therefore the
**apples-to-apples cluster comparison** the bun edition of this repo cannot
make (pm2 cannot cluster a Bun app — see `../bun`).

What it measures is the **overhead of managing** a Node server —
supervision, spawn route, daemon cost — not Node's raw HTTP performance and
not application logic. The application is deliberately minimal
(`server.mjs`): one fixed-body route and one `/health` route, no framework,
no database.

The full measured comparison lives in [`results/REPORT.md`](results/REPORT.md)
and as a self-contained page in [`results/REPORT.html`](results/REPORT.html)
(regenerated by `scripts/summarize.mjs` from the committed raw data). A
headline summary is reproduced below.

## Architecture

```
                    ┌──────────────────┐
                    │  autocannon      │  load generator (node)
                    │  c=10…1000       │  same machine, fixed payload
                    └────────┬─────────┘
                             │ HTTP
              ┌──────────────┴───────────────┐
              ▼                              ▼
     ┌────────────────┐             ┌────────────────┐
     │      pm2       │             │     pboss      │
     │  (god daemon,  │             │    (daemon)    │
     │   node)        │             │                │
     └───────┬────────┘             └───────┬────────┘
             │ spawns                       │ spawns
             ▼                              ▼
     ┌────────────────────────────────────────────┐
     │  node server.mjs  — THE SAME APPLICATION   │
     │  fork:    1 process                          │
     │  cluster: N workers, one node:cluster       │
     │           shared port (primary distributes) │
     └────────────────────────────────────────────┘
```

Both managers launch the exact same file with the exact same Node binary
(pinned absolute `NODE_BIN`; the pm2 daemon — and with it every
`cluster.fork()` worker, which inherits the daemon's execPath — runs under
that same binary), same port, same environment. The ONLY difference between
the two columns of every table is which process manager supervises the
server.

### Cluster mode, natively on both sides

`node:cluster` is THE clustering mechanism for Node apps, and both managers
use it:

- **pboss** `--instances N` selects pboss's node:cluster mode: pboss spawns
  ONE supervised process — a generated wrapper primary
  (`node-cluster-wrapper.mjs`) — which forks the N workers with
  `cluster.fork()`, gives every worker the same `PORT` (`--port` becomes
  `PBOSS_BASE_PORT`), respawns crashed workers with backoff, and reloads
  with zero downtime on SIGHUP.
- **pm2** `-i N` is true `cluster_mode`: the pm2 daemon itself becomes the
  cluster primary and forks the N workers with `cluster.fork()`.

Same worker count, same sharing mechanism (the primary's listening socket
distributed to workers), same application — the manager stays the only
variable, and the harness refuses to measure a cluster run unless the
manager is ACTUALLY running N workers.

## What is measured

| Metric | How | Better |
|---|---|---|
| Requests/sec | autocannon, discarded warmup then measured run | higher |
| p50/p90/p95/p99 latency | autocannon percentiles, median across repeats | lower |
| CPU usage | `/proc` utime+stime of the **whole tree** (daemon + server + every worker + pboss's wrapper primary), sampled every 500 ms | lower |
| Memory usage | `/proc` statm RSS of the whole tree | lower |
| Errors / timeouts / non-2xx | autocannon counters | zero |
| Cold startup | start command → first `200` from `/health`, daemon included | lower |
| Warm startup | daemon already up | lower |
| Idle daemon overhead | daemon alone, no application | lower |
| Crash recovery (fork) | `SIGKILL` the server → time to `200` again | lower |
| Crash recovery (cluster) | `SIGKILL` ONE worker → time to a replacement worker, and whether `/health` stayed up | lower / 100% |
| Restart storm | N manager restarts: failures, orphans, RSS growth (cluster: all workers must return) | none |

Every comparison table's last column is the **Winner**: the manager that
scored better on that row, with the relative difference
`(pboss − pm2) / pm2 × 100` beside it. Direction-aware — for throughput higher
wins, for everything else lower wins; exactly level reads “tie”.

## Running it

```bash
cd benchmarks/node
npm install          # autocannon + pm2, pinned as local devDependencies
```

Profiles (env `BENCH_PROFILE`):

| Profile | Connections | Duration | Repeats | Notes |
|---|---|---|---|---|
| `smoke` | 10, 100 | 5 s | 1 | verify the harness itself, ~2 min |
| `standard` *(default)* | 10, 100, 500 | 60 s | 5 | what this repo's results were run with |
| `full` | 10, 100, 500, 1000 | 60 s | 5 | adds the 1000-connection stress level |

```bash
BENCH_PROFILE=smoke bash scripts/benchmark.sh     # always smoke first
bash scripts/benchmark.sh                          # standard profile
BENCH_PROFILE=full bash scripts/benchmark.sh       # + 1000-conn stress
BENCH_INSTANCES=4 bash scripts/benchmark.sh        # cluster workers (default: cores)
```

Each profile runs **twice** — once in fork mode, once in cluster mode
(`BENCH_INSTANCES` workers, default one per core) — plus the mode-appropriate
startup, crash and storm phases.

By default the suite uses an **installed `pboss`** from `PATH`. To benchmark
a pboss repo checkout instead (what produced this repo's results):

```bash
PBOSS_CMD="bun run /path/to/pboss/src/main.ts" bash scripts/benchmark.sh
```

Useful variables: `BENCH_PORT` (default 3000), `BENCH_INSTANCES` (cluster
worker count, default `nproc`), `BENCH_RESULTS_DIR`, `SAMPLE_INTERVAL_MS`
(default 500), `SOAK_MINUTES` (default 0 — set e.g. 15 to add a
sustained-load phase to `crash-recovery.sh`). The cluster crash/storm phases
can also be run standalone: `BENCH_MODE=cluster bash
scripts/crash-recovery.sh`.

### Isolation & safety

Each manager runs under its own scratch home (`PBOSS_HOME` / `PM2_HOME`
under a `mktemp` dir) — a real install's daemon, dump and logs are never
touched, and everything is torn down on exit. The suite refuses to proceed
when the port stays occupied or server processes survive a teardown.

## Fairness rules

- Same `server.mjs`, same Node binary, same port, same machine, same load
  generator — only the manager differs.
- **Cluster mode: same worker count, same sharing mechanism** — pboss
  `--instances N` vs pm2 `-i N`, both N workers on one `node:cluster`
  shared port; a cluster run is skipped unless the manager really has
  N workers up.
- Every measured run starts from a **verified-clean state** (app deleted,
  daemon killed, port free, no orphans) — so each run also measures a cold
  start of the whole manager stack.
- A **discarded warmup** precedes every measured run.
- **Manager order alternates** between runs (load index + repeat parity).
- **Repeats with medians** — per-run numbers are recorded, not just the best
  one; the report lists every run.
- Crash/restart tests run as **separate phases** — a restart never
  contaminates throughput numbers.
- CPU/memory cover the whole tree (daemon + managed server + cluster
  primaries and workers), plus the manager's idle overhead with nothing
  running.

### Chunked execution (environments that cap process lifetime)

A full standard run takes a couple of hours of wall time. Where a single
long-lived process cannot run that long (CI containers, sandboxed sessions),
the same run can be split into chunks that accumulate into the same results
directory:

- `BENCH_PHASES=idle,warm-fork,matrix-fork,...` — run only the named phases
  this invocation (`idle`, `matrix-fork`, `warm-fork`, `matrix-cluster`,
  `warm-cluster`, `crash-fork`, `crash-cluster`; default all, in order).
- `BENCH_START_REPEAT` / `BENCH_END_REPEAT` — the repeat window for the
  matrix and warm-startup phases (e.g. `1..3`, then `4..5`).
- `BENCH_APPEND=1` — keep the existing results (skip the preflight wipe; the
  first chunk's `meta.json` stays the run's identity).

Every chunk ends with a summarize pass, so the report and the README's
summary always reflect exactly the data accumulated so far. The manager
alternation seed counts the runs already on disk, so a resumed chunk keeps
alternating exactly where the previous one left off.

```bash
# chunk 1 (fresh results): idle + startup phases
BENCH_PHASES=idle,warm-fork,warm-cluster bash scripts/benchmark.sh
# chunks 2..N (append): one (mode × load × repeat-window) at a time
BENCH_APPEND=1 BENCH_PHASES=matrix-fork BENCH_CONNECTIONS=10 \
  BENCH_START_REPEAT=1 BENCH_END_REPEAT=3 bash scripts/benchmark.sh
```

**What the data says** (this machine, this workload — computed from the fresh run):

- **Fork-mode throughput is a coin-flip at this load** (pboss (+0.0%) on mean RPS) — the manager is not in the request path; the operational metrics are where managing shows. Warm startup: pboss (-35.6%). 50-restart storm: pboss (-51.9%).
- **Cluster respawn after SIGKILL**: pboss (-38.3%) — pboss replaces a dead worker in ~93 ms vs pm2's ~151 ms. Cluster throughput at 100 connections: pboss (+4.6%).
- **Both managers survived the 50-restart fork storm with zero failures and zero orphans.**

<!-- auto-summary:end -->

- **Throughput is a wash in fork mode** (±0.2–5.5% either way across loads)
  — the manager is not in the request path. **In cluster mode pboss led
  2 of 3 loads** (+4.4% mean RPS at 100 connections, −5.3% mean latency;
  pm2 led c=500 by 2.1%).
- **pboss wins every startup and restart metric, in both modes**: cold
  −22%/−33%, warm −39%/−32%, 50-restart storm −52% (fork) and −42%
  (cluster). Fork crash recovery is pboss by half (70 vs 140 ms).
- **Worker respawn is the one clear pm2 win, and it is a design
  difference, not a bug**: pboss's node:cluster wrapper respawns a crashed
  worker with exponential backoff (observed: 0.4 → 0.7 → 1.3 → 2.5 → 4.9 →
  9.7 → 15 s, then capped) while pm2 restarts it immediately (~170 ms
  every time). Under the benchmark's rapid successive kills the backoff
  dominates; in a real crash-loop it is the behavior that protects the
  machine from fork-bombing. Either way **`/health` never dropped** — the
  surviving workers carried the shared socket through 100% of kills for
  both managers.
- **Memory: pboss is lighter in fork (−6%) and its cluster workers are
  lighter (−21% during the storm), but pm2's whole cluster tree is lighter
  at rest (−10.7%)** — pboss adds a wrapper primary process (its node:cluster
  model) that pm2 does not need (its daemon IS the primary).
- **Both managers survived both 50-restart storms with zero failures, zero
  orphans, zero measurable memory growth.**

One machine, one moment in time — re-run the suite before deciding
anything for your own hardware.
