pboss vs pm2 — managing a Bun HTTP server

The same server.ts, the same Bun executable, the same machine, the same load — the only difference is which process manager supervises it. This measures the overhead of managing a Bun server, not Bun's raw HTTP performance. Both supervision models are covered: fork (one managed process) and cluster (2 workers).

Methodology

  • Every measured run starts from a verified-clean state: app deleted, daemon killed, port free, no orphaned processes — each run is a cold start of the whole manager stack (that cold-start time is itself measured).
  • A discarded warmup run precedes every measured run.
  • Manager order alternates between runs (load index + repeat parity) so time-of-run bias cannot favor one column.
  • CPU and memory cover the whole process tree (daemon + managed Bun server), sampled from /proc every 0.5s during the measured run.
  • Crash-recovery and restart-storm runs are separate phases and never overlap the HTTP measurements.
  • Same-machine caveat: the load generator shares the CPUs with the servers; absolute numbers are specific to this box — compare the two columns, don't quote them as platform throughput.
  • Cluster mode runs the same matrix for every manager that can actually cluster a Bun app: pboss (its native process-based cluster, --instances N, workers sharing one SO_REUSEPORT port). pm2 cannot — its cluster mode is node:cluster inside the pm2 daemon and cannot wrap an app run with a non-Node interpreter — so it is reported as not supported in the cluster section, never measured with fork-mode numbers wearing a cluster label.

Winner names the column that scored better; the percentage beside it is the relative difference (pboss − pm2) / pm2 × 100 — positive means pboss scored the higher number. For throughput higher is better; for every other metric in these tables lower is better, and the Winner column already accounts for the direction. A row that is exactly level reads “tie”.

Cluster mode2 workers

pboss supervises N Bun workers of the same server.ts, all binding the same port through SO_REUSEPORT (the kernel balances connections across them) — its native process-based cluster, --instances N.

pm2: cluster mode — not supported (Bun apps). PM2's cluster mode is implemented with node:cluster inside its Node daemon: cluster.fork() always runs the daemon's own runtime and ignores --interpreter, and pm2 only selects cluster mode when the interpreter path contains "node" — so pm2 start -i N --interpreter bun silently runs the instances in fork mode (exec_mode: fork_mode, N plain processes, no port sharing), and forcing exec_mode: "cluster_mode" runs the workers under Node, not Bun. Rather than publish fork-mode numbers under a cluster label, this benchmark records pm2 as not supported and measures only pboss in this mode. (The node suite in this repo runs both managers' cluster modes.)

Reproduce

cd benchmarks/bun
npm install                     # pm2 + autocannon (local, pinned)
bash scripts/benchmark.sh       # default profile — BENCH_PROFILE=smoke first
BENCH_PROFILE=full bash scripts/benchmark.sh    # + the 1000-conn stress level
BENCH_INSTANCES=4 bash scripts/benchmark.sh      # cluster workers (default: cores)
# PBOSS_CMD="bun run /path/to/pboss/src/main.ts" bash scripts/benchmark.sh
Raw data: every number above traces to a file under results/raw/ — run.jsonl records, full autocannon JSON, /proc resource CSVs, recovery and storm event logs (fork and cluster each). results/summary.csv is the same data in one sheet. Don't read one run — the medians and the per-run notes show the repeats and the variability; a single run never decides a column.
