# pboss vs pm2 — managing a Bun HTTP server (fork + cluster modes)

A reproducible benchmark comparing **pboss** and **pm2** as process managers
for the **same Bun HTTP server**, on one machine, under identical load — in
both supervision models: **fork** (one managed process, both managers) and
**cluster** (N workers sharing one port — **pboss only**: pm2 cannot cluster
a Bun app, and this suite reports it as **not supported** rather than
measuring fork-mode instances under a cluster label).

What it measures is the **overhead of managing** a Bun server — supervision,
spawn route, daemon cost — not Bun's raw HTTP performance and not application
logic. The application is deliberately minimal (`server.ts`): one fixed-body
route and one `/health` route, no framework, no database.

The full measured comparison lives in [`results/REPORT.md`](results/REPORT.md)
and as a self-contained page in [`results/REPORT.html`](results/REPORT.html)
(regenerated by `scripts/summarize.mjs` from the committed raw data). A
headline summary is reproduced below.

## Architecture

```
                    ┌──────────────────┐
                    │  autocannon      │  load generator (node)
                    │  c=10…1000       │  same machine, fixed payload
                    └────────┬─────────┘
                             │ HTTP
              ┌──────────────┴───────────────┐
              ▼                              ▼
     ┌────────────────┐             ┌────────────────┐
     │      pm2       │             │     pboss      │
     │  (god daemon)  │             │    (daemon)    │
     └───────┬────────┘             └───────┬────────┘
             │ spawns                       │ spawns
             ▼                              ▼
     ┌────────────────────────────────────────────┐
     │  bun server.ts   — THE SAME APPLICATION    │
     │  fork:    1 process                          │
     │  cluster: N processes, one SO_REUSEPORT     │
     │           port, kernel-balanced              │
     └────────────────────────────────────────────┘
```

Both managers launch the exact same file with the exact same Bun executable,
same port, same environment. The ONLY difference between the two columns of
every table is which process manager supervises the server.

### Cluster mode, honestly

A Bun app cannot be wrapped in `node:cluster` — that API only runs Node
workers (pm2's cluster mode is `cluster.fork()` **inside its Node daemon**,
which always runs the daemon's own runtime and ignores `--interpreter`).
So "cluster" for a Bun app means **process-based clustering**: N independent
Bun workers all binding the same port through `SO_REUSEPORT`
(`reusePort: true` in `Bun.serve`, which `server.ts` enables when the harness
starts it with `BENCH_CLUSTER=1`). The kernel load-balances connections
across the workers.

- **pboss** supports this natively: `pboss start server.ts --instances N`
  (each worker gets `PBOSS_WORKER_ID` / `NODE_APP_INSTANCE`). The suite
  measures it.
- **pm2** does **not**: `pm2 start -i N --interpreter bun` silently
  downgrades to **fork mode** (`exec_mode: fork_mode` — N plain processes,
  no port sharing), and forcing `exec_mode: "cluster_mode"` runs the
  workers under **Node**, not Bun. The suite therefore records pm2 as
  **not supported** in cluster mode (`raw/pm2/cluster-unsupported.json`,
  cited in the report) and never measures it there — no fork numbers
  wearing a cluster label.

(The `node` suite in this repo runs the same matrix with Node apps, where
pm2's cluster mode genuinely works — the comparison this suite cannot
make.)

Same server file, same worker count where both managers run — the manager
stays the only variable, and the harness refuses to measure a cluster run
unless the manager is ACTUALLY running N workers.

## What is measured

| Metric | How | Better |
|---|---|---|
| Requests/sec | autocannon, discarded warmup then measured run | higher |
| p50/p90/p95/p99 latency | autocannon percentiles, median across repeats | lower |
| CPU usage | `/proc` utime+stime of the **whole tree** (daemon + server + every worker), sampled every 500 ms | lower |
| Memory usage | `/proc` statm RSS of the whole tree | lower |
| Errors / timeouts / non-2xx | autocannon counters | zero |
| Cold startup | start command → first `200` from `/health`, daemon included | lower |
| Warm startup | daemon already up | lower |
| Idle daemon overhead | daemon alone, no application | lower |
| Crash recovery (fork) | `SIGKILL` the server → time to `200` again | lower |
| Crash recovery (cluster) | `SIGKILL` ONE worker → time to a replacement worker, and whether `/health` stayed up | lower / 100% |
| Restart storm | N manager restarts: failures, orphans, RSS growth (cluster: all workers must return) | none |

Every comparison table's last column is the **Winner**: the manager that
scored better on that row, with the relative difference
`(pboss − pm2) / pm2 × 100` beside it. Direction-aware — for throughput higher
wins, for everything else lower wins; exactly level reads “tie”.

## Running it

```bash
cd benchmarks/bun
npm install          # autocannon + pm2, pinned as local devDependencies
```

Profiles (env `BENCH_PROFILE`):

| Profile | Connections | Duration | Repeats | Notes |
|---|---|---|---|---|
| `smoke` | 10, 100 | 5 s | 1 | verify the harness itself, ~2 min |
| `standard` *(default)* | 10, 100, 500 | 60 s | 5 | what this repo's results were run with |
| `full` | 10, 100, 500, 1000 | 60 s | 5 | adds the 1000-connection stress level |

```bash
BENCH_PROFILE=smoke bash scripts/benchmark.sh     # always smoke first
bash scripts/benchmark.sh                          # standard profile
BENCH_PROFILE=full bash scripts/benchmark.sh       # + 1000-conn stress
BENCH_INSTANCES=4 bash scripts/benchmark.sh        # cluster workers (default: cores)
```

Each profile runs **twice** — once in fork mode, once in cluster mode
(`BENCH_INSTANCES` workers, default one per core) — plus the mode-appropriate
startup, crash and storm phases.

By default the suite uses an **installed `pboss`** from `PATH`. To benchmark
a pboss repo checkout instead (what produced this repo's results):

```bash
PBOSS_CMD="bun run /path/to/pboss/src/main.ts" bash scripts/benchmark.sh
```

Useful variables: `BENCH_PORT` (default 3000), `BENCH_INSTANCES` (cluster
worker count, default `nproc`), `BENCH_RESULTS_DIR`, `SAMPLE_INTERVAL_MS`
(default 500), `SOAK_MINUTES` (default 0 — set e.g. 15 to add a
sustained-load phase to `crash-recovery.sh`). The cluster crash/storm phases
can also be run standalone: `BENCH_MODE=cluster bash
scripts/crash-recovery.sh`.

### Isolation & safety

Each manager runs under its own scratch home (`PBOSS_HOME` / `PM2_HOME`
under a `mktemp` dir) — a real install's daemon, dump and logs are never
touched, and everything is torn down on exit. The suite refuses to proceed
when the port stays occupied or server processes survive a teardown.

## Fairness rules

- Same `server.ts`, same Bun executable, same port, same machine, same load
  generator — only the manager differs.
- **Cluster mode: same worker count, same sharing mechanism** — pboss
  `--instances N` vs pm2 `-i N`, both N independent Bun processes on one
  `SO_REUSEPORT` port; a cluster run is skipped unless the manager really has
  N workers up.
- Every measured run starts from a **verified-clean state** (app deleted,
  daemon killed, port free, no orphans) — so each run also measures a cold
  start of the whole manager stack.
- A **discarded warmup** precedes every measured run.
- **Manager order alternates** between runs (load index + repeat parity).
- **Repeats with medians** — per-run numbers are recorded, not just the best
  one; the report lists every run.
- Crash/restart tests run as **separate phases** — a restart never
  contaminates throughput numbers.
- CPU/memory cover the whole tree (daemon + managed server), plus the
  manager's idle overhead with nothing running.

### Chunked execution (environments that cap process lifetime)

A full standard run takes a couple of hours of wall time. Where a single
long-lived process cannot run that long (CI containers, sandboxed sessions),
the same run can be split into chunks that accumulate into the same results
directory:

- `BENCH_PHASES=idle,warm-fork,matrix-fork,...` — run only the named phases
  this invocation (`idle`, `matrix-fork`, `warm-fork`, `matrix-cluster`,
  `warm-cluster`, `crash-fork`, `crash-cluster`; default all, in order).
- `BENCH_START_REPEAT` / `BENCH_END_REPEAT` — the repeat window for the
  matrix and warm-startup phases (e.g. `1..3`, then `4..5`).
- `BENCH_APPEND=1` — keep the existing results (skip the preflight wipe; the
  first chunk's `meta.json` stays the run's identity).

Every chunk ends with a summarize pass, so the report and the README's
summary always reflect exactly the data accumulated so far. The manager
alternation seed counts the runs already on disk, so a resumed chunk keeps
alternating exactly where the previous one left off.

```bash
# chunk 1 (fresh results): idle + startup phases
BENCH_PHASES=idle,warm-fork,warm-cluster bash scripts/benchmark.sh
# chunks 2..N (append): one (mode × load × repeat-window) at a time
BENCH_APPEND=1 BENCH_PHASES=matrix-fork BENCH_CONNECTIONS=10 \
  BENCH_START_REPEAT=1 BENCH_END_REPEAT=3 bash scripts/benchmark.sh
```

## Caveats

- The load generator shares the machine with the servers (a dedicated load
  client would be cleaner); absolute numbers are specific to this box —
  compare the columns, don't quote them as platform throughput.
- pboss's daemon runtime follows its install channel (bun on a bun-channel
  install); the environment block in REPORT.md states exactly what ran.
- One machine, one moment in time. Re-run the suite on your own hardware
  before making decisions that matter to you.
